1Quick start

Everything lives under frontend/. The suite needs no Flask backend, no InventDB instance, and no network — the API is answered inside the browser. 

# one-time, after cloning
cd frontend
npm install
npx playwright install chromium

# run
npm run test:e2e
CommandDoes
npm run test:e2eFull suite, headless, both device profiles
npm run test:e2e:uiUI mode — watch, time-travel, pick locators. Best place to write tests
npm run test:e2e:headedDesktop profile with a visible browser
npm run test:e2e:mobilePixel 7 profile only
npm run test:e2e:reportOpen the HTML report from the last run
npm run typecheck:e2eType-check the test files (not part of npm run build)

Useful flags

npx playwright test login                 # only files matching "login"
npx playwright test -g "signs in"         # only tests whose title matches
npx playwright test --project=chromium    # skip the mobile profile
npx playwright test --debug               # step through with the inspector
npx playwright test --repeat-each=3       # flake hunting
npx playwright show-trace test-results/…/trace.zip
The dev server starts itself. Playwright runs npm run dev and waits for port 5173. If a dev server is already running there it reuses it instead — so a stale server with an invalidated dependency cache can affect a local run. If results look impossible, stop your dev server and let Playwright start its own.

Ten of the eleven spec files drive the real React app in a real browser. contract.spec.ts is different in kind: it never opens a page, it validates the fake API itself.

Coverage by feature area

  • Every module. Properties, Owners, Tenants, Leases, Work Orders, Vendors, Inspections, Compliance, Daily Tasks and Accounting are each driven through the same generic list contract, because they are one component configured by src/config/entities.ts.
  • Every route. All 14 sidebar destinations plus the two unmatched-route behaviours (single unknown segment renders “Unknown module”; a deeper unknown path redirects to the dashboard).
  • Both themes' plumbing. Theme toggling from the topbar and the settings card, persistence across reload, and the pre-paint stamp on <html>.
  • Failure paths, not just happy paths. Roughly a quarter of the assertions are about what happens when the API returns 400, 401, 409, 500, 502, 503, or simply never answers.

3How it is wired together

Projects

Three projects run in dependency order:

ProjectRunsProfile

The mobile profile exists because the layout genuinely changes below 820px — the sidebar becomes a drawer — and below 960px, where the login hero reflows via display: contents. Those are different behaviours, not the same page at a different size, so they get their own tests rather than a resize inside a desktop test.

Fixtures

Specs import test from ./fixtures rather than from Playwright directly. That extended test supplies:

NameKindPurpose
storeFixtureA fresh, mutable copy of the seed data for this test
mockApiAuto fixtureInstalls the fake API before the test body runs. Specs never request it
liveApiOptiontest.use({ liveApi: true }) skips mocking entirely
apiLatencyOptionDelays every API response, for asserting on loading states
Why store does not depend on page. It would be natural to build the store and install the routes in one fixture. Doing so creates a page → store → page cycle once the auto fixture needs both, which Playwright rejects at load time. Keeping store pure and putting the installation in a separate auto fixture avoids it.

4Authentication

AuthContext gates every route behind a user and token held in localStorage (pms.token and pms.user). Signing in once per test would be slow and would put the same assertions in every file, so the setup project does it once and saves the resulting browser state.

That state is produced by driving the real login form — not by writing the token directly. If the login contract changes, the failure appears in one obvious place instead of silently handing every other test a shape the app no longer accepts. The setup also pins pms.theme to light, so theme assertions do not depend on the machine's colour-scheme preference.

Starting a test signed out

import { signedOut, test } from "./fixtures";

test.use(signedOut);   // clears the saved state for this file

login.spec.ts uses this for the form itself and for the route-protection checks. There is also a signIn(page) helper for tests that need to sign in mid-test.

5The mocked API

fixtures/mock-api.ts installs one route handler for every same-origin /api/ call and dispatches internally by path. One broad handler rather than a dozen narrow ones is deliberate: Playwright matches handlers in reverse registration order, so with many overlapping patterns the effective precedence becomes hard to reason about. With a single handler installed by the fixture, a page.route() a spec registers later always wins — which is exactly the override behaviour the failure tests need.

Writes mutate the per-test store. A create really does appear in the list refetch React Query fires afterwards, so the assertions exercise the full round trip rather than just inspecting the outgoing request.

Overriding one endpoint

await page.route("**/api/dashboard/summary", (route) =>
  route.fulfill({
    status: 500,
    contentType: "application/json",
    body: JSON.stringify({ error: "InventDB is unreachable" }),
  })
);
await page.reload();

await expect(page.locator(".alert.error")).toHaveText("InventDB is unreachable");

Overriding only some methods

Call route.fallback() to defer to the mock for the requests you did not mean to change: 

await page.route("**/api/properties", (route) => {
  if (route.request().method() !== "POST") return route.fallback();
  return route.fulfill({ status: 400, contentType: "application/json",
                         body: JSON.stringify({ error: "street must be unique" }) });
});

Extending the mock

Add a branch in the dispatch chain in mock-api.ts, keyed on the first path segment. Two rules matter:

  • Match /api/ at the root of the path, not anywhere in the URL. The handler uses a regex rather than a glob for this reason. In development Vite serves the app's own source files at their real paths, and some of those paths contain /api/ — a pattern loose enough to catch them will intercept application code. The comment above the regex in mock-api.ts explains it in full; leave it there.
  • Envelope endpoints should come from the contract, not by hand. If the backend composes the response itself, serve the recorded one via backendResponse(key) — see §6.

Seed data

fixtures/data.ts holds three properties, two of everything else, plus dashboard, report and workflow payloads. Field names mirror src/config/entities.ts exactly, because the UI reads records by those names — a drifting fixture shows up as a blank cell rather than a clear failure. Every record carries an _id, which is what the edit and delete paths key off.

6The contract layer

A mocked API has one structural weakness: it can agree with itself forever while drifting away from the real backend. A renamed field or a dropped envelope would leave the whole suite green against a backend it no longer describes.

The contract layer closes that gap. backend/tests/contract/ replays recorded InventDB responses through the real Flask app, validates the output against contract/api-contract.json, and publishes the app's actual responses to contract/responses/. contract.spec.ts then holds the mock to the same contract and the same responses. Drift on either side now fails on that side.

Regenerate after changing a backend response shape:

cd backend
UPDATE_CONTRACT=1 python -m pytest tests/contract

The mock serves recorded responses for envelope endpoints — metadata and other bodies the backend composes itself. Per-record fixtures stay in data.ts, because those exist to drive assertions on specific rendered values, and a captured dataset would change them every time someone edited the demo instance.

The validator in contract.spec.ts is a deliberate re-implementation of the Python one in backend/tests/contract/spec.py, not a shared module. A validator generated from the backend would agree with the backend by construction, which is the one thing it must not do.

7Writing a new test

import { dialog, expect, field, row, rows, test } from "./fixtures";

test("creates a vendor", async ({ page }) => {
  await page.goto("/vendors");
  await page.getByRole("button", { name: "New Vendor" }).click();

  await field(page, "company").fill("Summit Roofing");
  await dialog(page).getByRole("button", { name: "Save" }).click();

  await expect(page.locator(".toast.success")).toHaveText("Vendor created");
  await expect(row(page, "Summit Roofing")).toBeVisible();
});

Conventions that keep tests stable

Headings repeat — always pass a level

The layout renders the page title as an <h1> in the topbar, and entity pages repeat the same text as an <h2>. Asking for the heading by name alone matches both and fails strict mode. 

page.getByRole("heading", { name: "Properties", level: 1 })   // topbar
page.getByRole("heading", { name: "Properties", level: 2 })   // page head

Labels are substring-matched by default

getByLabel("Password") also matches the show/hide toggle, whose aria-label is “Show password”. Use { exact: true } on the login and settings forms.

Use field() for entity forms

Required labels render as Street*, which defeats exact label matching, while loose matching makes Phone ambiguous with Emergency Phone. Every control has a stable id="f-<name>", which is what the helper targets.

Counting charts

Recharts gives legend icons their own .recharts-surface. Count .recharts-wrapper when you mean “how many charts”.

Prefer round-trip assertions

Because writes mutate the store, assert on the resulting row rather than only on the outgoing request. Check the request payload as well when type coercion matters — numeric and currency fields are converted out of their string form before sending, and untouched fields are omitted rather than sent empty.

Do not add waitForTimeout. Every locator and assertion already retries until it passes or times out. A fixed sleep either makes the suite slower than it needs to be or hides a real race. The search box is debounced by 300ms and the assertions absorb that without help.

9What is not covered

Stated plainly, because a green suite invites more confidence than it earns.

  • No backend Python runs. During a frontend test run the Flask app is not started. Backend behaviour is covered by the separate pytest suite in backend/tests/, and the two are joined only by the contract layer in §6.
  • No real InventDB. Nothing here proves the app works against a live instance — only against responses shaped like one.
  • Per-record fixtures are assumptions. The contract pins envelope shapes. The individual records in data.ts are hand-written, so a field renamed in the real schema would not fail here.
  • No visual regression. Layout is asserted structurally and through the mobile overflow guard, not by pixel comparison.
  • No accessibility audit. Tests use accessible roles and names throughout, which exercises the accessibility tree incidentally, but nothing runs an axe-style ruleset.
  • Chromium only. Both profiles are Chromium-based. Firefox and WebKit are installed but no project targets them.
  • Passing tests are weak evidence of correctness. The assertions were written by reading the current implementation, so they largely encode today's behaviour as correct. Their value is catching tomorrow's regression, not proving today's code right.

10Troubleshooting

SymptomLikely cause
Blank page, timeout waiting for any element The app did not boot. Check the browser console rather than the test output — run the same navigation with a page.on("pageerror") listener. A route pattern intercepting application code is the usual cause
strict mode violation: resolved to 2 elements An ambiguous locator. Add level: to headings, exact: true to labels and text, or scope to a container
Element “intercepts pointer events” Something overlays the click target — usually an open drawer or modal scrim. Click a position that is actually exposed
Currency or date assertions fail locale or timezoneId lost from the config
Contract tests fail after a backend change Expected. Regenerate with UPDATE_CONTRACT=1 (§6), then update the mock to match
Local run behaves impossibly A stale dev server on 5173 is being reused. Stop it and let Playwright start its own
Fixture dependency cycle at startup A fixture was made to depend on page which something else needs first. See the note in §3

For anything that fails on a retry, the trace is the fastest route to an answer — it carries a DOM snapshot, the network log and the console for every step: npx playwright show-trace test-results/…/trace.zip.

11Running in CI

- run: npm ci
  working-directory: frontend

- run: npx playwright install --with-deps chromium
  working-directory: frontend

- run: npx playwright test
  working-directory: frontend

- uses: actions/upload-artifact@v4
  if: ${{ !cancelled() }}
  with:
    name: playwright-report
    path: frontend/playwright-report/

Setting CI changes four things automatically: retries go to 2, workers drop to 2, test.only becomes an error rather than a silent filter, and the dev server is always started fresh instead of reusing whatever is on 5173.

Consider adding npm run typecheck:e2e as a CI step. It is deliberately not part of npm run build, so a type error in a test file will not block a deploy — which means nothing catches it unless CI runs it explicitly.
