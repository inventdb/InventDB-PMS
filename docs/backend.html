02

How it works

One seam, replaced

The application reaches InventDB through exactly one function call. Replacing that single call swaps out the whole upstream while leaving every layer above it real — URL construction, header building, error parsing, and the SQL the routers compose.

The obvious alternative, replacing the InventDBClient class, would mean the tests assert against a mock of the very code they are supposed to be testing. This way a test can state the property that actually matters: given this request, the application sent InventDB exactly this statement. 

def test_arbitrary_query_params_become_equality_filters(api, fake):
    api.get("/api/properties", query_string={"city": "Mumbai"})

    assert fake.sql_log[0] == (
        "SELECT * FROM pms.properties WHERE city = 'Mumbai' "
        "ORDER BY street ASC LIMIT 500 OFFSET 0"
    )

The same seam is what lets the suite prove the injection defence end-to-end. A hostile value goes in through an ordinary HTTP query string, and the test checks the statement that came out the other side is still one inert literal — not by pattern-matching the text, but by counting quotes, which is the actual invariant.

No network, no database, no fixtures to reset

Nothing in the suite opens a socket or needs a running InventDB. That is what keeps it at nine seconds, and it also means the tests can exercise the failure paths a live instance would never produce on demand: an unreachable host, a malformed error body, a namespace that doesn't exist yet.

03

The contract layer

The problem it solves

The frontend's Playwright suite runs against an API written by hand in e2e/fixtures/mock-api.ts. That fake is only useful while it matches the real backend, and nothing was checking that. A renamed field or a dropped envelope would leave 183 frontend tests green against a backend they no longer described.

InventDB a real instance
→capture
recordings what it replied
→replay
the real Flask app not a mock of it
→publish
contract/ shapes + responses

Both suites then validate against contract/: pytest checks the backend produces it, Playwright checks the mock matches it. A change on either side that the other hasn't followed fails on that side.

Two guards against rot

A contract test that quietly stops testing anything is worse than no test at all, so two things are enforced. If the application issues a query no recording covers, that's reported as a failure rather than answered with an empty result set. And any endpoint that replays to an empty response is rejected — otherwise a file full of empty envelopes would satisfy every shape check while proving nothing.

What it caught on the first run

Two pieces of drift in the hand-written mock, both invisible until now: /api/meta/entities was returning {name, key} when the real backend returns six fields, and every mocked error response omitted the ok: false that the backend always sends. The entities response is now served from the backend's own captured output rather than being rebuilt by hand.

The recordings shipped here are synthetic. They're shaped like InventDB's responses but the values are invented, because this repository holds no credentials. Running capture.py against your instance replaces them with real ones — it drives the actual application with a recorder attached, so whatever the app asks InventDB for is what gets recorded, and the recordings update themselves when the app's queries change. It reads only by default; capturing the write endpoints is an explicit opt-in because it creates and deletes a record in the live namespace.

Findings — the six that matter

Ordered by what each would cost if it went wrong. Numbering matches backend/tests/README.md.

01

Values containing a backslash may not be safely escaped

Needs a decision — I can't answer this one for you

What happened

When the application puts a user's value into a SQL statement, it wraps it in quotes and doubles any quotes inside — the standard defence. It does not touch backslashes.

Why it matters

Whether that's correct depends entirely on which SQL dialect InventDB speaks. Under strict SQL rules a backslash inside a quoted value is just a backslash, and the current code is right. Under MySQL-style rules a backslash is an escape character, and a value ending in a lone backslash would escape the closing quote and break out of the literal — a live injection.

I couldn't resolve it by guessing, because guessing the other way is also harmful: escaping backslashes on an engine that doesn't need it would corrupt legitimate data. A Windows file path stored in a note field would come back with doubled separators.

What to do

Find out how InventDB's SQL engine treats a backslash inside a quoted string. If it's an escape character, sql_literal needs one more line. If it isn't, the current behaviour is correct and this can be closed. The test that pins today's behaviour is already written either way.

02

Record ids go into the upstream URL unchecked

The guard already exists — it just isn't wired up

What happened

When you open a record, its id is pasted straight into the address the backend calls on InventDB. A caller who puts a ? in that id appends their own parameters to the internal API call; a # silently truncates the path.

Why it matters

It isn't a privilege escalation — the call still carries the caller's own token, so InventDB's row-level security still applies. But it hands a caller partial control over a request the backend makes on their behalf, which is the wrong shape of thing to leave lying around. Directory traversal via encoded slashes is separately blocked by the web framework's router, so that avenue is already closed.

The odd part is that the validator for exactly this already exists in the codebase, is documented as being for exactly this, and is applied to report ids — just never to record ids.

What to do

One call per site. I left it alone only because it would break every record read if InventDB's real internal ids turn out to contain characters outside letters, digits, hyphens and underscores — worth confirming against a live instance first.

03

The raw-SQL endpoint only inspects the first word

Closeable without knowing whether it's exploitable

What happened

/api/meta/sql lets a signed-in caller run a query, and protects itself by refusing anything that doesn't start with SELECT or WITH. A statement like SELECT 1; DROP TABLE … starts with SELECT, so it passes the check and is forwarded to InventDB word for word.

Why it matters

Whether that's dangerous depends on whether InventDB's SQL endpoint executes more than one statement per request. I couldn't verify that without an instance, so this is recorded as an open question rather than a confirmed hole.

What to do

Reject statements containing a semicolon anywhere but the very end. That closes it regardless of the answer, and costs nothing — no legitimate read query needs an interior semicolon.

04

One kind of upstream error is reported as a server crash

Known defect — test is written and marked

What happened

When InventDB returns an error, the backend reads the message out of it and passes it on with the original status. It assumes the error body is an object. If InventDB ever returns a list of errors — the usual shape for field-level validation failures — reading it fails, and the user sees a generic 500.

Why it matters

The real status is lost. A 422 "these three fields are wrong" becomes "internal error", so the interface can't show the user what to fix, and whoever investigates starts by looking in the wrong place.

What to do

A type check before reading the message. Three lines.

05

A malformed page size returns 500, with the Python error in the body

Known defect — test is written and marked

What happened

Requesting /api/properties?limit=abc crashes the handler. The response is a 500 whose body contains the raw interpreter message (invalid literal for int()…).

Why it matters

A malformed query string is the client's mistake and should be a 400. A 500 tells monitoring the server is broken when it isn't, so this is the kind of thing that erodes trust in an alert channel. The report endpoints handle the identical situation correctly, which makes the inconsistency harder to spot than the bug itself.

What to do

Coerce with a fallback, the way /api/reports/renewals already does with its days parameter.

06

Two helpers with the same name disagree about money

Silently wrong numbers — no error, no warning

What happened

The dashboard and the reports each have a helper for turning a stored value into a number. They share a name and a purpose but not their tolerance. The dashboard's strips currency symbols and thousands separators before converting; the reports' does not, and falls back to zero when conversion fails.

Why it matters

InventDB is schemaless, so an amount can perfectly well be stored as the text "1,500". When it is, that lease contributes 1500 to the dashboard's expected rent and 0 to the rent roll's monthly total. Two pages, two different answers, from the same record, with nothing on screen to suggest anything went wrong.

This is the finding I'd expect to cause an argument in a meeting before anyone traces it to code.

What to do

Delete one of them and share the tolerant version. The test that demonstrates the divergence is in test_reports.py.

05

Four rough edges

07 A missing value is labelled “None” on the charts
The dashboard means to show “Unknown” when a record has no status. Because of how the fallback is written, an absent column stringifies to the literal word "None" instead, while a blank one correctly becomes “Unknown”. The legend can end up showing both slices, meaning the same thing. Cosmetic, but it looks like a data problem.
08 The report rollups ignore the configured namespace
Six endpoints hardcode pms rather than reading the namespace from configuration, unlike every other router. Harmless today; deploy against a differently-named namespace and those six break while the rest of the application keeps working — which is a confusing way to find out.
09 Unexpected errors echo their message to the client
The catch-all handler puts the exception text into the response body. That's genuinely convenient in a demo instance, and it's why finding 05 above is as visible as it is. Worth revisiting before this faces anyone untrusted, since an exception message can carry a connection string.
10 A helper that nothing calls, and its docstring is wrong
like_literal claims to escape search wildcards. It doesn't, so a user searching for 100% would match every row. Nothing calls it, so nobody has hit this — but a future caller would reasonably trust the docstring. Fix it or delete it.
06

Already fixed

  • Three identifier allow-lists accepted a trailing newline. All three used a pattern anchored with $, which in Python also matches immediately before a final newline — so "properties\n" passed a check that was never meant to accept it. Not exploitable on its own, but an allow-list that accepts a character it didn't intend to is worth closing. Now anchored properly. This was safe to change without asking, because no legitimate identifier ends in a newline.
  • The frontend mock's entity metadata was missing four fields. It returned {name, key}; the backend returns six fields. It now serves the backend's captured response instead of a hand-written one.
  • The frontend mock's error responses were missing ok: false. The backend includes it on every failure. Now the mock does too.

Running it

# the whole suite — no network, no InventDB needed
cd backend
pip install -r requirements-dev.txt
python -m pytest

# just the cross-suite contract checks
python -m pytest -m contract

After changing a response shape

Republish the contract, then confirm the frontend mock followed: 

cd backend && UPDATE_CONTRACT=1 python -m pytest tests/contract
cd ../frontend && npx playwright test contract.spec.ts

Replacing the synthetic recordings with real ones

cd backend
INVENTDB_BASE_URL=https://<slug>.cloud.inventdb.com \
INVENTDB_USERNAME=you INVENTDB_PASSWORD=... \
python -m tests.contract.capture

Reads only by default. Pass --include-writes to also capture create, update and delete — that writes to the live namespace, creating one property and removing it again. Credentials are stripped from everything before it's written to disk, and a test checks that the stripping worked, since these files are committed.

Where this sits relative to the frontend suite. The 183 Playwright tests cover the interface with the API faked inside the browser; these 732 cover the API with InventDB faked below it. The contract layer is the only place the two meet, and it now fails loudly rather than silently when they disagree. What still isn't covered by either: the real InventDB instance itself, and whether the per-record fixtures in e2e/fixtures/data.ts resemble real data — those remain assumptions.
