Two things worth knowing about the new test suite

A Playwright suite of 135 tests now covers the PMS frontend. Two points came out of building it that are worth understanding — one is a quirk of the app's markup that catches out anyone writing a new test, and one is a decision left deliberately open for you.

Suite: 135 tests, all passing (~30s) Scope: Frontend only — backend untested Location: frontend/e2e/
01

The app says the same thing twice, and tests can't pick between them

Not a defect — just something test writers must know

What happened

When you're on the Properties page, the word “Properties” appears twice as a heading: once large in the top bar, and again slightly smaller on the page itself. When a test says “find the heading called Properties”, it finds two, refuses to guess which one you meant, and fails.

The login form has the same shape of problem. The password box is labelled “Password”, and the eye icon that reveals it is labelled “Show password”. Ask for “Password” and you match both, because the default search is a loose “contains this text” match.

Why it matters

This is not a bug in the app. The markup is perfectly reasonable and the duplicate heading is a deliberate design choice. But it catches out anyone writing their first test here, and the resulting error message doesn't obviously point at the cause.

What to do

Be specific rather than loose: ask for “the top-level heading” instead of just “the heading”, and “exactly the word Password” instead of “anything containing password”. For form fields there's a small helper — field(page, "street") — that sidesteps the problem entirely by targeting each input's stable id.

02

The test type-checker exists, but isn't wired into your build

Open decision — yours to make

What happened

There's now a command, npm run typecheck:e2e, that catches type mistakes inside the test files themselves. It is not connected to npm run build.

Why it matters

If it were connected, a typo in a test file would stop you shipping the application. Some teams want exactly that — tests and code held to one standard, nothing broken gets out. Others find it infuriating when they're trying to push a hotfix at 6pm and a stale test file blocks the build.

That's a judgement about how strict your pipeline should be, and it affects everyone who deploys. It isn't a technical question with a right answer, so it wasn't decided on your behalf.

What to do

Nothing, if you're happy running it manually or in CI. If you want it enforced at build time, it's a one-line change to the build script in frontend/package.json.

One caveat that belongs alongside these two. This suite covers the frontend only. During a run the Flask backend isn't even started — every API call is answered inside the browser, and no Python in backend/ is executed. A separate pytest suite under backend/tests/ now covers that side directly, and the contract recordings there replay real Flask responses into the frontend's fake ones, so the envelope shapes can't quietly drift apart. The per-record fixtures in e2e/fixtures/data.ts are still hand-written, so those remain an assumption rather than a guarantee.
